光脑方案-局限三-全局生长调度器单点瓶颈解决方案

一、问题定义

局限名称：全局生长调度器单点瓶颈

问题描述：当前架构中，全局生长调度器（GGS）位于前额叶内部，统一接收各模块的生长请求，分配资源配额，维护生长日志。这种集中式设计在以下场景中存在风险：

1. 性能瓶颈：多模块同时发起生长请求时，调度器成为串行化点，限制系统吞吐量。
2. 单点故障：若前额叶模块失效，整个系统的生长能力停滞，已积累的生长日志可能丢失。
3. 扩展受限：分布式部署时，集中式调度器难以跨节点协调，各节点生长状态无法同步。

根本原因：生长调度器被设计为单一中心化组件，缺乏去中心化的协调机制和故障转移能力。

二、解决方案总览

针对上述问题，设计了四个递进方向：

方向 定位 核心思想 当前状态
去中心化生长授权 核心机制 各模块自主决定生长，前额叶仅配额分配与日志审计 详细设计完成
协调者存活性探测 故障容错 心跳超时切换到自治模式，保障协调者故障时生长不停滞 详细设计完成
配额预分配 资源策略 融入核心机制，作为去中心化生长的具体实现方式 详细设计完成
分片生长调度 远期扩展 按模块或领域分片，多调度器实例并行 仅可行性推理

三、核心方案：去中心化生长授权（含配额预分配）

3.1 机制概述

将生长决策权从前额叶下放到各模块内部。前额叶从实时审批者转变为战略资源分配者，定期计算并分配配额。各模块在配额内根据本地误差信号自主触发生长，异步上报日志。

3.2 配额管理器：动态配额分配算法

3.2.1 总配额计算公式

```
总配额 = 基础配额 × 成熟度衰减因子 × 负载调节因子
```

参数 含义 建议值/计算方式
基础配额 系统初始设定的每周期最大生长量 可配置，如神经网络100连接/天，符号知识50条/天
成熟度衰减因子 系统越成熟，生长越慢 exp(-λ × maturity)，λ默认0.5
负载调节因子 高负载时抑制生长 负载<50%:1.0；50%-80%:0.7；>80%:0.3

3.2.2 各模块分配公式

```
模块配额 = 总配额 × (模块权重 × 模块效率得分) / Σ(各模块权重 × 效率得分)
```

参数 含义 计算方式
模块权重 模块的基础重要性 丘脑:0.3，小脑:0.4，海马体:0.2，其他:0.1（可配置）
效率得分 近期生长带来的性能增益 (当前性能 - 历史基线) / 近期生长消耗

3.2.3 配额分配伪代码

```
算法：动态配额分配
Input: 各模块历史效率记录 E，系统成熟度 M，当前负载 L
Output: 各模块配额分配表

1. base_quota = config.base_quota
2. maturity_factor = exp(-0.5 × M)
3. load_factor = 1.0 if L<0.5 else (0.7 if L<0.8 else 0.3)
4. total_quota = base_quota × maturity_factor × load_factor
5. for each module m:
       efficiency[m] = (perf_current[m] - perf_baseline[m]) / cost_recent[m]
       weighted[m] = config.weight[m] × efficiency[m]
6. sum_weighted = sum(weighted)
7. for each module m:
       quota[m] = total_quota × weighted[m] / sum_weighted
8. return quota
```

3.3 配额生命周期管理

阶段 操作 说明
分配 前额叶定时（如每小时）计算并广播新配额 配额带有效期，超时未使用部分作废
消费 模块每次生长时扣减配额 原子操作，防止超额
结转 当期未用完的配额可按比例结转至下一周期 结转比例30%，避免囤积
回收 连续多周期未使用的配额被回收重新分配 检测到模块长期低效时触发

四、容错方案：协调者存活性探测

4.1 机制概述

前额叶定期向各模块广播存活信号。各模块维护超时计数器，若连续多次未收到信号，判定协调者不可用，自动切换到自治生长模式，采用保守配额继续生长，并将日志缓存至本地，待协调者恢复后补传。

4.2 状态定义与转换

状态 含义 触发条件
正常模式 协调者存活，使用动态配额 收到存活信号
探测模式 单次未收到信号，暂不切换 1次探测超时
自治模式 协调者判定为故障，使用保守配额 连续3次探测超时
恢复过渡模式 协调者刚恢复，上传缓存日志 自治模式下首次收到存活信号

状态转换逻辑：

```
正常模式 ──(超时1次)──> 探测模式 ──(收到信号)──> 正常模式
探测模式 ──(再超时2次，累计3次)──> 自治模式
自治模式 ──(收到信号)──> 恢复过渡模式 ──(日志上传完成)──> 正常模式
```

4.3 状态机伪代码

```
算法：协调者存活性探测状态机
Input: 当前状态 S，本轮是否收到存活信号 received
Output: 新状态 S_new，当前有效配额 Q

1. match S:
2.     Normal:
3.         if not received: S_new = Probing, Q = dynamic_quota
4.         else: S_new = Normal, Q = dynamic_quota
5.     Probing:
6.         if received: S_new = Normal, Q = dynamic_quota
7.         else if miss_count >= 3: S_new = Autonomous, Q = dynamic_quota × 0.5
8.         else: S_new = Probing, Q = dynamic_quota
9.     Autonomous:
10.        if received: S_new = Recovering, Q = autonomous_quota
11.        else: S_new = Autonomous, Q = autonomous_quota
12.    Recovering:
13.        if upload_complete: S_new = Normal, Q = dynamic_quota
14.        else: S_new = Recovering, Q = dynamic_quota × 0.5
15. return S_new, Q
```

4.4 自治模式下的保守策略

参数 值 说明
配额比例 50% 取上次正常配额的50%，或使用预设默认值
最大持续时间 24小时 超过后暂停生长，等待人工介入
日志缓存上限 10000条 超出后丢弃最旧的日志

4.5 日志缓存与补传

4.5.1 缓存日志结构

```rust
struct CachedGrowthLog {
    id: String,                 // 唯一标识
    timestamp: u64,             // 生长发生时间
    module: ModuleId,           // 来源模块
    action: GrowthAction,       // 生长操作类型
    detail: String,             // 操作详情（JSON）
    quota_consumed: f32,        // 消耗配额
    retry_count: u32,           // 补传重试次数
}
```

4.5.2 补传流程

```
恢复过渡模式启动：
1. 与协调者建立连接，发送缓存日志数量
2. 协调者返回可接收窗口大小（一次最多1000条）
3. 模块分批上传，每批确认
4. 单次上传失败：最多重试3次，指数退避（1秒、2秒、4秒）
5. 连续3次失败：标记该日志为“待人工处理”，跳过继续上传后续
6. 协调者进行冲突检测
7. 上传完成，模块清空缓存，切换回正常模式
```

4.5.3 冲突仲裁规则

冲突类型 仲裁规则
知识条目写入冲突 比较确定性，高者保留，低者移入沉寂库
配额消耗冲突 以协调者记录为准，模块端修正本地计数器
时间戳冲突 以生长实际发生时间为准，协调者日志排序

五、远期扩展：分片生长调度

5.1 基本原理

将生长调度职责按模块类型或知识领域进行分片，每个分片由独立调度器实例负责。实例之间通过一致性哈希确定职责边界，各分片内自治，跨分片协调通过轻量分布式共识解决。

5.2 理论可行性

· 分片是分布式系统的标准扩展模式，在数据库、缓存、消息队列中已广泛验证。
· 光脑方案的生长调度本质是资源分配+日志记录，天然适合分片。
· 一致性哈希、Raft/Paxos等算法为跨分片协调提供成熟理论基础。

5.3 当前处理

光脑方案v0.1.0定位为单机理论验证，分片调度作为远期扩展，仅保留设计接口，不做详细实现。
