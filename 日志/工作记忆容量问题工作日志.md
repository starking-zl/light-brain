光脑方案-局限八-工作记忆容量解决方案

一、问题定义

局限名称：工作记忆容量

问题描述：当前架构中，前额叶工作记忆设计为固定容量（7±2个符号组块）。在复杂推理任务或长时间对话中，工作记忆可能溢出，导致早期上下文丢失、推理链断裂。多轮对话中的指代消解、跨轮推理等场景对工作记忆容量提出了更高要求。

根本原因：工作记忆固定容量与变长推理链之间的结构性矛盾。并非所有场景都需要大容量，但缺乏按场景分层的弹性扩展机制。

二、设计哲学

1. 场景分层，而非一刀切。
工作记忆的容量需求随场景变化而显著不同。正常对话中7±2容量充足；复杂任务中需要临时扩展暂存区；跨会话任务需要持久化恢复。与其设计一套复杂的通用弹性机制，不如按场景特征分层处理，各层机制独立、互不干扰。

2. 工作记忆只负责“当前在思考什么”。
工作记忆的本质是推理的“寄存器”，不是记忆的“仓库”。需要扩展的不是工作记忆本身，而是“思考的中间结果如何暂存和恢复”。暂存交给工作记忆库，持久化交给小脑，历史回溯交给海马体。工作记忆保持轻量，容量固定。

3. 压缩而非丢弃。
当工作记忆需要腾出空间时，不简单淘汰最旧的组块，而是将属于同一子任务的多个组块压缩为一个摘要组块。信息不丢失，只是粒度变粗。需要细节时，可从工作记忆库解压恢复。

三、场景分层方案

场景 特征 持续时间 核心机制
正常对话 单次会话内的话题延续、指代消解、轻度推理 数分钟至数十分钟 保持现有7±2容量，自然轮替淘汰
长时间工作 复杂任务跨越多轮对话，需记住中间结论、分步骤结果 同一会话内持续数小时 工作记忆库分页暂存 + 组块压缩 + 阶段性总结
超长时间工作 任务跨越多天、多次会话，需恢复上次工作状态 数天至数周 任务快照持久化至小脑，会话间恢复

四、正常对话场景

策略：保持现有设计，无需改动。

当前工作记忆容量7±2符号组块足以覆盖绝大多数日常对话。组块自然轮替：新组块进入，最旧且不重要的组块被淘汰。前额叶调度时直接从工作记忆读取最近状态，无额外开销。

五、长时间工作场景：工作记忆库

5.1 工作记忆库的定位

工作记忆库是前额叶内部的一个会话级轻量暂存区，专门存放被“分页”出去的工作记忆组块。它与海马体有本质区别：

对比项 工作记忆 工作记忆库 海马体
存储内容 活跃推理组块 被分页的压缩组块 完整对话事件
容量 7±2组块 每会话最多50组块 大规模事件
生命周期 当前推理链 当前会话内 跨会话持久化
检索方式 直接访问 任务ID索引 多模式查询

5.2 分页触发

当工作记忆组块数达到阈值（固定为7个）且新组块需要进入时，触发分页压缩。压缩不是简单淘汰最旧的组块，而是将属于同一子任务的多个组块压缩为一个摘要组块。

5.3 组块压缩算法

可压缩性得分：对于任意两个组块A和B，计算综合得分判断它们是否属于同一子任务。

```
Score(A, B) = α × EntityOverlap(A, B) 
            + β × TopicSimilarity(A, B) 
            + γ × TemporalProximity(A, B) 
            + δ × IntentContinuity(A, B)
```

维度 计算方式 权重（建议）
实体重合度 ` A.entities ∩ B.entities
话题相似度 cosine(A.topic_vector, B.topic_vector) β=0.3
时序邻近度 `exp(- A.timestamp - B.timestamp
意图连贯性 预定义意图连贯矩阵查询 δ=0.1

压缩簇识别：

1. 构建相似度图：以组块为节点，两两之间若Score > 压缩阈值θ（建议0.6）则建立边。
2. 识别连通分量：找出图中的连通分量，每个连通分量即为一个候选“子任务簇”。
3. 选择压缩目标：优先压缩节点数最多的簇；若多个簇节点数相同，取簇内平均边权重最高的簇。
4. 生成摘要组块：将该簇内所有组块压缩为一个SummaryChunk。

5.4 摘要组块结构

```rust
struct SummaryChunk {
    id: String,                       // 唯一标识
    description: String,              // 子任务简要描述（由布罗卡区生成）
    entities: Vec<String>,            // 簇内高频实体
    topic_vector: Vec<f32>,           // 簇内组块向量的平均
    compressed_ids: Vec<String>,      // 被压缩的原始组块ID列表（存于工作记忆库）
    status: TaskStatus,               // Active / PendingConfirm / Completed
    created_at: u64,
}
```

被压缩的原始组块移入工作记忆库，仅保留摘要组块在工作记忆中（占用1个槽位）。

5.5 解压与召回

当用户追问涉及摘要组块中的细节时（如“那个航班的起飞时间是几点？”），前额叶检索到相关摘要组块，根据compressed_ids从工作记忆库调回原始组块，替换摘要组块。若原始组块过多，可只调回与当前追问最相关的几个。

5.6 显式压缩

当用户说“总结一下”或“整理一下刚才的内容”时，丘脑识别意图为“指令请求”且包含总结关键词，前额叶直接触发压缩。压缩范围由用户指定或由前额叶根据当前活跃话题自动界定。

5.7 工作记忆库容量管理

工作记忆库容量上限为50个组块（含原始组块和摘要组块），超出后按LRU淘汰旧组块。淘汰前检查该组块是否已被摘要组块引用，若有则保留引用关系。

六、超长时间工作场景：任务快照

6.1 任务快照的持久化

当用户在一个会话中进行了复杂任务，会话结束时，光脑可主动询问：“这次的任务进度需要保存吗？下次可以继续。”

若用户同意，前额叶将当前工作记忆和工作记忆库中的所有组块整合为一个TaskSnapshot，以小脑知识条目的形式存储。

```json
{
  "subject": "任务快照",
  "attribute": "旅行规划-20260418",
  "value": {
    "description": "三天北京旅行规划，已确定航班和酒店，待确认景点",
    "entities": ["北京", "航班", "酒店"],
    "chunks": "[序列化的工作记忆组块]",
    "created_at": 1713456789,
    "last_updated": 1713456789
  }
}
```

6.2 任务恢复

用户下次开启新会话时，通过“继续上次的XX任务”指令唤醒。光脑从小脑检索该任务快照，将其反序列化加载回工作记忆和工作记忆库，同时从海马体检索任务时间段（任务起止时间±1小时）内的历史事件作为背景上下文，快速恢复工作状态。

七、边界情况处理

边界情况 处理策略
压缩后摘要组块仍然过多（超过7个） 对摘要组块再次压缩，生成更高层级的元摘要
用户主动要求“忘记”某任务 从工作记忆库删除对应组块，若已存入小脑则标记删除
会话异常中断 工作记忆库内容丢失，下次会话可从小脑恢复已保存的快照
用户同时进行多个任务 工作记忆库按任务ID分区存储，互不干扰
任务快照版本更新 用户继续任务后重新保存，覆盖旧快照或生成新版本

八、与光脑现有架构的集成

组件 新增内容 位置

分页与压缩逻辑 组块超阈值时触发，归纳同子任务组块 前额叶
摘要描述生成 布罗卡区根据簇内组块生成简要描述 布罗卡区

十、总结

问题 回答
能否解决工作记忆容量不足？ 能。通过场景分层，正常对话保持轻量，长时间工作用工作记忆库暂存，超长工作用任务快照持久化。
方案是否臃肿？ 否。各场景机制独立，正常对话零开销，仅在需要时启用扩展机制。
与现有架构是否冲突？ 否。工作记忆库是前额叶内部扩展，任务快照复用小脑和海马体现有接口。
